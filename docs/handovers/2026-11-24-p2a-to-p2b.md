## How plans are written and verified here

As in P1 and P2a (see the P1→P2 handover for the full procedure): read the real plans' structure
outside fences, ask the open questions, and stop. Then build in a scratch clone outside the
repository (`git clone -c core.autocrlf=false`), one commit per task, with the gate at every
commit. Generate the plan from the scratch history, run `planrun check` on it, and replay it on a
fresh clone with `core.autocrlf=true`. Copy it to `docs/plans/` and stop for review.

The P2a session's scripts were in its scratchpad; they are gone, so rewrite them. Pieces:

- `run_gates.py`: checks out each commit, runs the gate and the task's targeted command, and
  stores the summary lines with `finished in …s`.
- `gen_plan.py`:
  - full contents from `git show`, an exact diff for changed files over 300 lines;
  - a fence one backtick longer than any backtick run at 0–3 spaces of indentation in its body;
  - a commit step with the blob ids of every staged file.
- `replay.py`: writes the full-contents blocks, `git apply`s the diffs, runs gate + commit in one
  pwsh session per task, and checks `git status --porcelain` after each.

Gotchas found in P2a, in addition to the P1 ones:

- **Final newlines.** A full-contents block always ends in a newline, so a file without one gets
  a different blob id and the commit step refuses. Check every touched file for a final newline
  in the scratch history before generating the plan. Several `tests/corpus/invalid/*.md` and
  `.vscode/tasks.json` still have none.
- **Git Bash heredocs that feed Python turn `\b` into a backspace** (and `\\n` into a newline).
  Write edit scripts with the Write tool, and scan tracked files for control characters before a
  commit.
- `python -I` drops the script's directory from `sys.path`, so a local helper module no longer
  imports. Use plain `python` for your own scripts.
- When copying `tests/corpus/local/` into a clone, copy only `20*.md`: the README is tracked, and
  copying it over dirties the tree.
- New or changed insta snapshots: run `INSTA_UPDATE=always cargo test`, then review the diff of
  each `.snap` file. A changed snapshot is a review item; say why in the plan.
- In a commit step that stages files, only the task's files may be staged: the plan's own file is
  already committed.
